# 사용자 제보 설계

작성 2026-09-08 · 상태: 확정 (구현 계획 대기)

## 1. 배경

`2026-07-24-data-reality-gap-design.md`는 368행에서 "사용자 신고·크라우드소싱은 범위 밖"이라고 선을 그었다. 이 문서가 그 선을 연다.

원본 공공데이터에는 우리가 알고리즘으로 잡을 수 없는 오류가 있다. 좌표 한 자리 오타나 명백한 구역 이탈은 `scripts/audit-data.mjs`가 잡아내지만, "이 자리에 은행나무가 아니라 느티나무가 있다", "여긴 나무가 아예 없다", "여기 가로수가 있는데 데이터에 없다"는 **현장을 본 사람만 안다.**

## 2. 원칙

이 셋은 이후 어떤 변경에서도 유지된다.

1. **원본 불변** — 공공데이터 스냅샷(`public/data/*.json`)은 수정하지 않는다. 정정은 오버레이로만 남기고 `method: 'user-report'` / `confidence: 'reported'`로 자동 교정과 구분 표시한다. (`2026-07-24-data-reality-gap-design.md` §4.1) — 오버레이 구현은 이번 범위 밖이다(§7).
2. **승인 전 비공개** — 제보는 관리자 검토·승인 전까지 지도에 일절 반영되지 않는다. 자동 반영 경로를 만들지 않는다.
3. **거부 시 파기** — 거부한 제보 자료(특히 사진)는 되돌릴 수 없이 사라져야 한다.

## 3. 접근 — 이미 있는 창구를 쓴다

**사용자가 메일·X·GitHub로 제보하고, 앱은 위치 정보를 대신 채워준다.**

앱 안에 제보 폼도, 서버 엔드포인트도, 파일 저장소도 만들지 않는다. 세 창구는 PR #20에서 이미 만들어 `ContactPanel`에 노출돼 있다.

이 선택이 지우는 것:

| 짓지 않는 것 | 이유 |
|---|---|
| `POST /api/submissions` · 업로드 토큰 엔드포인트 | 제보가 우리 서버를 거치지 않는다 |
| 파일 저장소(Vercel Blob 등) | 사진은 메일 첨부 · GitHub 이슈 첨부 · X 이미지로 온다 |
| 레이트리밋 · 악용 방어 | 공개 엔드포인트가 없다. Upstash 부재와 무관해진다 |
| `public/privacy.html` (이 기능 한정) | 폼으로 연락처를 수집하지 않는다 — 사용자가 자기 메일·계정으로 보내므로 우리가 수집 주체가 아니다. **Phase 2b 푸시 구독에는 여전히 필요하다** |
| 레코드별 식별자 배정 | 제보 위치는 주소·좌표로 온다. 어느 레코드인지는 검토 때 사람이 판단한다 |

원칙 3(거부 시 파기)은 저장소를 두지 않음으로써 자동 충족된다. 우리가 보관하는 사진이 없다.

## 4. 진입점

`src/components/Map.jsx`의 팝업 조립부는 세 갈래이고, `.street-view-btn`이 이미 클릭 위임으로 붙어 있다. 같은 방식으로 `.report-btn`을 단다.

| 진입점 | 채워지는 정보 |
|---|---|
| 개별 가로수 팝업 (`buildMarkerInfo`) | 좌표 · 지역 · 도로명 · 수종 · 식재본수 · 출처 기관 · 기준일 |
| 가로수길 구간 팝업 (`buildPolylineInfo`) | 위 + 구간 그루수 (기관은 `pl.representative`) |
| 명품숲 팝업 (`buildFamousForestInfo`) | 주소 · 수종 · 면적 · 관리기관 |
| 로드뷰 모달 (`StreetViewModal`) | 위 + 보고 있던 지점. `treeData` prop으로 레코드를 이미 받고 있다 |
| `ContactPanel` (사이드바) | 없음 — 위치는 사용자가 적는다 |

**로드뷰 모달이 가장 중요한 진입점이다.** "실제로 나무가 없다"를 발견하는 곳이 바로 로드뷰다.

`ContactPanel`은 마커가 없는 제보(누락된 나무 등)를 받는다. 지도 중심 좌표를 배선할 수도 있으나 App↔Map 사이에 상태가 하나 늘어난다. 첫 제보를 받아보고 필요하면 그때 넣는다.

## 5. 창구별 링크

신설 모듈 `src/utils/reportLinks.js`에 **순수 함수만** 둔다.

```
buildReportContext(item)  →  { title, location, shown, mapUrl }
reportMailHref(ctx)  /  reportGithubHref(ctx)  /  reportXHref(ctx)
```

### 메일

`src/data/contact.js`의 `mailHref()`에 `&body=`를 추가한다. 사용자가 좌표를 손으로 옮겨 적어야 한다면 아무도 제보하지 않는다.

```
제목: [식물 알레르기 지도] 데이터 제보 — 서울특별시 강남구 테헤란로

■ 위치
  좌표: 37.522895, 127.020205
  지역: 서울특별시 강남구 · 도로명: 테헤란로
  지도: https://map.naver.com/p?c=127.020205,37.522895,17,0,0,0,dh

■ 지도에 표시된 정보
  구분: 서울 가로수 (개별) · 수종: 은행나무 · 식재본수: 1본
  데이터 기준: 2026-04-29

■ 제보 내용 (아래에 적어주세요)
  무엇이 틀렸나요:
  실제 정보:
  (사진이 있으면 첨부해 주세요)
```

### GitHub

`issues/new?template=data-report.yml&<필드id>=<값>`으로 이슈 폼을 미리 채운다.

### X

280자 제약이 있어 좌표 · 지역 · 표시된 수종까지만 넣는다. 나머지와 사진은 사용자가 붙인다.

### 인코딩

세 링크 모두 `encodeURIComponent`를 거친다. 팝업 HTML은 `escapeHtml`을 쓰므로 **URL 생성과 HTML 삽입을 분리한다** — 인코딩 두 층이 섞이면 깨진다. 도로명·수종에 `&`와 따옴표가 든 실제 레코드가 있어 여기가 가장 부서지기 쉽다.

지도 링크의 일반 지도(파노라마 아님) URL 형식은 **2026-09-13 확정**: `https://map.naver.com/p?c=<lng>,<lat>,17,0,0,0,dh`. map.naver.com에서 서울 강남(127.0276, 37.4979)·부산(129.0756, 35.1796) 두 좌표로 열어 지역 표시가 각각 "강남구 역삼1동"·"연제구 연산2동"으로 뜨는 것을 확인했다. 이 확인은 네이버 쪽 URL만 쓰므로 우리 프로덕션을 거치지 않아도 된다. `naverMapUrl()`로 `naverLinks.js`에 두고, 메일 본문의 `■ 위치` 블록 끝에만 넣는다 — GitHub 위치 칸과 X의 280자에는 좌표 텍스트로 충분하다.

## 6. GitHub 이슈 템플릿

`.github/ISSUE_TEMPLATE/data-report.yml`을 신설한다. 현재 `.github`에는 `workflows/ci.yml`뿐이다.

GitHub Issue Forms로 만들고 **필드 id를 쿼리 파라미터로 프리필**한다. 라벨은 템플릿 frontmatter에 둔다 — `?labels=` 쿼리 파라미터는 triage 권한이 없는 제보자에게 무시되기 때문이다.

```yaml
name: 데이터 제보
labels: [제보, 데이터]
body:
  - 위치 (주소 또는 좌표)      # required. 마커 없는 제보도 이걸로 받는다
  - 무엇이 틀렸나요             # dropdown: 수종 / 위치 / 없는 나무 / 누락된 나무 / 기타
  - 실제 정보 (아는 만큼)
  - 사진                       # 드래그&드롭 첨부 안내
  - 지도에 표시된 정보           # 프리필. 사용자는 손대지 않는다
  - 데이터 출처 · 기준일         # 프리필
```

`config.yml`도 함께 두어 이슈 생성 화면에서 메일·X를 대체 창구로 안내한다.

템플릿 본문에 원칙 1·2를 명시한다 — 제보가 원본을 바꾸지 않으며 검토 후 반영된다는 것.

## 7. 이번 범위 밖 — 승인된 제보의 지도 반영

**반영 메커니즘은 이 문서의 범위가 아니다.** 첫 제보 몇 건을 실제로 받아본 뒤 별도로 설계한다.

이유:

- 반영하려면 `public/data/user-reports.json` 오버레이 + **소스별 매칭 함수 3개**가 필요하다. 서울은 현재 오버레이 키가 배열 인덱스라 사실상 신설이다
- 제보가 0건이다. 어떤 필드가 정정 대상으로 올지, 매칭 단위가 무엇이어야 하는지 전부 추측이다
- 명백한 오류는 그동안에도 `audit-data.mjs` 경로로 고칠 수 있어 완전히 막히지 않는다

**설계할 때 이미 확인해 둔 제약:**

- `scripts/audit-data.mjs`가 `public/data/corrections.json`을 **통째로 덮어쓴다.** 승인된 제보를 거기 넣으면 다음 `npm run audit:data`에서 전부 사라진다. 별도 파일이어야 하고, `src/services/api.js`의 `getQualityOverlay()`가 셋째 파일로 읽어야 한다
- **정정은 레코드 하나가 아니라 구별 불가능한 묶음에 걸린다.** 소스에 그 이상 쪼갤 필드가 없다 — 서울은 좌표·수종·구·도로명을 모두 조합해도 4,797건(1.9%)이 충돌하며 최대 89그루가 한 키를 공유하고, 전국은 정체성 필드를 다 써도 105개 그룹(268건)이 갈리지 않는다. 관리자가 이슈에서 몇 건에 걸리는지 보고 건별로 판단한다
- 승인 항목의 selector가 원본 갱신 후 아무것도 매칭하지 못하면 오버레이가 조용히 사라진다. `audit-data.mjs`에 매칭 건수 검증(0건이면 실패 리포트)을 붙인다
- 신뢰도 표기는 `method: 'user-report'` / `confidence: 'reported'`. `src/services/api.js`의 `CONFIDENCE_RANK`에 값을 추가한다

## 8. 테스트 전략

메모리 `test-the-real-request-shape`의 교훈을 적용한다 — **실제 데이터에서 뽑은 레코드로** 링크를 만든다. 손으로 만든 목은 실제 경로를 밟지 않는다.

| 대상 | 방법 |
|---|---|
| `reportLinks.js` | 단위 테스트. `sttree-roads.json` · `seoul-trees.json` · `famous-forests.json`의 실제 레코드 사용 |
| 실제 결측 케이스 | 도로명 미상(`sanitizeRoadName`이 비운 서울 7,130그루) · 수종 빈 값 · 좌표 0 · 기관 없음 → "미상"으로 표시되고 링크가 깨지지 않는지 |
| 특수문자 | 도로명·수종에 `&` `"` `#` 공백이 든 실제 레코드로 URL 인코딩 검증 |
| X 280자 | 가장 긴 지역명·도로명 조합에서 절단이 정상 동작하는지 |
| 팝업 렌더 | `Map.test.jsx`의 기존 naver 목에 이어, 세 팝업 + 로드뷰 모달에 제보 링크가 들어가는지 |
| 이슈 템플릿 | CI에서 YAML 파싱 + **프리필에 쓰는 필드 id가 템플릿에 실제로 존재하는지** 검증. id 오타는 GitHub이 조용히 무시하므로 눈에 띄지 않는다 |
| 프로덕션 실측 | 승격 후 팝업 → 메일 / GitHub / X 링크를 눌러 본문이 채워지는지. 네이버 지도 URL 형식도 여기서 확정 |

지도 관련 변경이므로 브라우저 실측은 머지·승격 이후 프로덕션에서만 가능하다(메모리 `naver-maps-domain-lock`).

# 로드뷰 현실과 공개 데이터의 격차 해소 — 설계

작성일: 2026-07-24
상태: 설계 확정 대기

## 1. 문제

로드뷰로 확인한 현장과 우리가 표시하는 가로수 데이터가 자주 어긋난다.
사용자가 지목한 유형은 세 가지다.

1. 수종이 다름
2. 위치가 어긋남
3. 나무가 아예 없음

## 2. 조사 결과 — 문제의 실제 구성

전국 10,423구간과 서울 257,186그루를 전수 검사한 결과, 이 격차의 상당 부분은
**로드뷰를 보기 전에 데이터만으로 판정 가능한 오류**였다. 측정값은
`docs/superpowers/specs/2026-07-24-data-audit.md`에 별도 기록한다.

핵심 수치:

| 발견 | 규모 |
|---|---|
| 서울 강동구청 등록 좌표가 평균 23.9km 어긋남 | 61건 전원 |
| 대구 군위군청 / 경북 청도군청 좌표 오류 | 각 4/4, 3/3 (100%) |
| 수종명 칸이 `결주`(빈 자리)·`고사`(죽은 나무) | 서울 303그루 |
| 오타·축약형 탓에 알레르기 등급이 0으로 떨어짐 | 서울 2,904그루 |
| 도로명 칸이 무효값(`3`, `6`, `은행나무` 등) | 서울 7,130그루 |
| 직선거리가 신고 연장보다 김 (물리적 모순) | 전국 1,709구간 |
| 복수 수종이 한 칸에 기재되어 두 번째 종 정보 소실 | 전국 3,102구간 |
| 국토 밖 좌표 | 전국 9건 |

### 2.1 가장 위험한 결함

`getAllergenInfo()`가 `speciesName.includes(keyword)` 부분일치를 쓴다. 이 때문에
축약형 `양버즘`이 정식명 `양버즘나무`와 매칭되지 않아, **알레르기 등급 3(높음)인
플라타너스가 "해당없음"으로 표시된다.** 의료 맥락에서 false negative는 가장
위험한 오류 방향이다.

같은 이유로 `왕벚`(152), `목백합`(83), `배롱`(32), 메타세쿼이아 오타 4종(337)이
등급 0으로 떨어진다.

### 2.2 검증된 자동 교정

한쪽 끝점만 국토 밖인 9건에 대해, 잘못된 끝점의 각 자릿수를 0~9로 치환한 후보 중
정상 끝점 5km 이내로 들어오는 것을 찾았다. **5건이 단일 후보로 확정 교정됐고
모호한 경우는 0건이었다.**

```
부산 동래구 금강로59번길  120.076932 → 129.076932  (앵커거리 0.20km)
충북 옥천 가화길           26.305441 →  36.305441  (앵커거리 0.22km)
경북 상주 상주보~         158.239748 → 128.239748  (앵커거리 0.57km)
충북 충주 충주산단2로       39.012237 →  37.012237  (앵커거리 1.95km)
광주 북구 북부순환도로     32.2148246 → 35.2148246  (앵커거리 3.20km)
```

### 2.3 자동 교정하면 안 되는 것

강동구청 61건은 오프셋이 일정하지 않다 (lat 0.211 ± 0.028, lng 0.038 ± 0.037).
일괄 평행이동은 부적절하다. **플래그만 세우고 교정하지 않는다.**

## 3. 조사로 배제된 접근

### 3.1 로드뷰 이미지 저장 파이프라인 — 약관 위반 소지

NCP AI·NAVER API 서비스 이용약관 원문:

> "'고객'은 '회사'의 사전 동의 없이 '본 서비스'의 결과 데이터를 본 약관에서
> 허용한 범위를 넘어서서 무단으로 복제, 저장, 가공, 배포하거나 제3자에게
> 제공해서는 안됩니다."

> "…별도로 저장해서는 안되며, 따라서 그와 같은 결과 데이터를 별도로
> 저장하는 방식으로 데이터베이스화하여 이용해서도 안됩니다. … 리턴 받는 즉시
> 1회 자신의 서비스에서 사용하는 것만 허용되며…"

네이버·카카오 모두 로드뷰 정지 이미지를 반환하는 공식 REST API가 없다.
Playwright로 파노라마를 캡처해 축적하는 파이프라인은 위 조항에 포섭될
가능성이 높다. **채택하지 않는다.**

### 3.2 수종 자동 판별 — 정확도 미달

| 근거 | 수치 |
|---|---|
| StreetTree 벤치마크(1,220만 장, 8,363종) 최고 모델 종 단위 top-1 | 29.45% |
| Auto Arborist 스트리트뷰 단독 class-averaged recall | 46.13% |
| 100속 분류 평균 F1 | 0.55 (범위 0.06~0.88) |
| 실제 가로수 대장 대조 매칭률 | 67.1% |
| 앱 6종의 수피 사진 종 식별 | "완전히 신뢰 불가" (PlantSnap 속 정확도 1.36%) |

낙엽수는 1년 중 6개월(11~4월) 잎이 없다. 상위 10종으로 클래스를 줄이면 개선
여지가 있으나 **한국 데이터 실측치가 존재하지 않으며**, 다수 2종(은행나무 42% +
양버즘나무 27%)이 가중 정확도를 부풀려 소수 종의 실패를 가린다.

**수종 자동 판별은 이번 범위에서 제외한다.**

### 3.3 살아남은 것

`panorama.getLocation()`이 공식적으로 다음을 반환한다.

```javascript
{ panoId, title, address, coord, photodate }
```

이미지를 저장하지 않고 **메타데이터만으로** 촬영 시점·실제 위치·주소를 얻을 수
있다. 이것이 Layer 1의 근거다.

## 4. 설계

### 4.1 원칙

**우리는 source of truth가 아니다.** 원본 공공데이터는 절대 덮어쓰지 않는다.
교정은 근거와 신뢰도를 가진 별도 오버레이로 관리하고, 화면에서 원본과 교정을
구분해 보여준다. 자동으로 판정할 수 없는 것은 고치는 척하지 않고 불확실한
상태 그대로 노출한다.

### 4.2 구조

```
공공데이터 원본 (불변)
        │
        ├─ Layer 0 · 빌드타임, 결정론적, 이미지 불필요
        │    scripts/audit-data.mjs        → public/data/quality-flags.json
        │    src/data/speciesCanonical.js  → 수종명 정규화 사전
        │    public/data/corrections.json  → 좌표 교정 오버레이 (근거 포함)
        │
        ├─ Layer 1 · 런타임, 로드뷰 메타데이터, 이미지 불필요
        │    panorama.getLocation() → 거리 / 주소 대조 / 촬영일자 대조
        │
        └─ UI · 검증 상태와 근거를 사용자에게 노출
```

각 레이어는 독립적으로 배포 가능하다. Layer 0만 먼저 배포해도 개선 효과가 있다.

### 4.3 Layer 0 — 데이터 정합성

#### 4.3.1 `src/data/speciesCanonical.js` (신규)

수종명 원본 문자열을 정규 형태로 바꾸는 순수 함수 모듈. 다른 어떤 것에도
의존하지 않는다.

```javascript
canonicalizeSpecies(raw) → {
  species: string[],      // 정규화된 수종명 배열 (복수 수종 분해됨)
  kind: 'tree' | 'not-a-tree' | 'unknown',
  raw: string,            // 원본 보존
  normalized: boolean,    // 교정이 적용되었는지
}
```

처리하는 것:

- **오타 교정**: `메타세콰이어`·`매타세콰이아`·`메타세과이어`·`메타세퀘이아` → `메타세쿼이아`,
  `왕벗나무` → `왕벚나무`, `므티나무` → `느티나무`, `은해나무`·`은헹나무` → `은행나무`
- **축약형 확장**: `왕벚` → `왕벚나무`, `양버즘` → `양버즘나무`, `배롱` → `배롱나무`,
  `목백합` → `튤립나무`, `느티` → `느티나무`, `은행` → `은행나무`, `이팝` → `이팝나무`
- **복수 수종 분해**: `은행나무+이팝나무` → `['은행나무', '이팝나무']`.
  구분자 `+`, `,`, `/`, `·`, `외 N`, `등`
- **비수종 값 분류**: `결주`, `고사`, `공분`, `×`, `?`, 숫자 문자열 → `kind: 'not-a-tree'`
- **빈값/미상**: `kind: 'unknown'`

사전은 데이터에서 실측한 라벨을 근거로 작성한다. **추측으로 항목을 늘리지 않는다.**
사전에 없는 라벨은 원본 그대로 통과시키고 `normalized: false`로 표시한다.

#### 4.3.2 `src/data/allergenDatabase.js` (개편)

**부분일치를 없애지 않는다.** 매칭을 3단계로 만든다.

```
1. 별칭 테이블 정확 매칭  (신규, 신뢰도 exact)
2. 기존 부분일치 폴백      (유지, 신뢰도 inferred)
3. 미매칭                  (신뢰도 unknown)
```

부분일치를 정확 매칭으로 전면 교체하는 안을 검토했다가 폐기했다. 현재
부분일치로 **정상 동작하는 라벨이 1,646개**이기 때문이다 — `대왕참나무`(401)가
`참나무`로, `은단풍`(1,228)이 `단풍`으로, `스트로브잣나무`(136)가 `잣나무`로
매칭되고 있다. 이를 전부 별칭 테이블에 옮기지 않고 정확 매칭으로 바꾸면
대규모 회귀가 발생한다.

진짜 결함은 부분일치 자체가 아니라 **방향**이다. `getAllergenInfo`는
`라벨.includes(키워드)`만 본다. 라벨 `양버즘`이 키워드 `양버즘나무`보다
짧으면 영원히 매칭되지 않는다. 축약형이 전부 여기서 탈락한다.

따라서 1단계 별칭 테이블이 축약형·오타를 흡수하고, 2단계 부분일치는
기존 동작을 그대로 보존한다. 반환값에 `matchType: 'exact' | 'inferred'`를
실어 화면에서 추정 매칭임을 구분할 수 있게 한다.
- 복수 수종을 위해 `getAllergenInfos(species[]) → info[]` 추가.
  기존 `getAllergenInfo`는 단일 종용으로 유지.
- 등급 표시는 **최댓값**을 쓰되, 꽃가루 시기·증상은 **모든 종의 것을 병기**한다.
  현재는 첫 매칭 하나만 보여준다.
- 누락 수종 추가: 감나무(921), 층층나무(298), 살구나무(217), 산딸나무(106),
  모과나무(86), 히말라야시다(43), 대추나무(39), 꽃사과(25), 팥배나무(23),
  때죽나무(15), 후박나무, 먼나무, 가시나무, 담팔수, 동백, 모감주나무, 워싱턴야자.
  괄호는 서울 소스 실측 그루수. 알레르기 등급은 **근거를 확인한 것만** 부여하고,
  근거를 못 찾은 종은 등재하지 않는다 — 억지 등급보다 "정보 없음"이 낫다.

- **`level: 0`의 의미를 바로잡는다.** 현재 DB의 34개 항목 중 `level: 0`인 것은
  하나도 없다(실측: level 1이 14개, 2가 5개, 3이 8개, 4가 6개). 즉 지금 0은
  오직 "매칭 실패"를 뜻하는데 화면에는 **"해당없음"**으로 표시된다.
  "알레르기 유발 안 함"과 "몰라서 판정 못 함"이 같은 라벨을 쓰고 있는 것이다.
  의료 맥락에서 이 둘을 합치면 안 된다.

  0에 실제 항목이 없으므로 새 상태 키를 추가할 필요 없이 **라벨만 고치면 된다**:
  `'해당없음'` → `'정보 없음'`, 설명은 `'DB에 등재되지 않은 수종입니다'`,
  색은 healthcare-clean의 pending(`#475569`)을 재사용한다.
  Legend·FilterPanel·StatsPanel은 `ALLERGEN_LEVELS`를 그대로 순회하므로
  코드 변경 없이 반영된다.

#### 4.3.3 `scripts/audit-data.mjs` (신규)

두 소스를 읽어 레코드별 플래그를 산출하고 `public/data/quality-flags.json`으로 저장.

전국 소스 플래그:

| 코드 | 의미 | 현재 건수 |
|---|---|---:|
| `COORD_OUT_OF_KR` | 좌표가 국토 밖 | 9 |
| `COORD_WRONG_REGION` | 좌표가 등록기관 시도 밖 | 163 |
| `LENGTH_CONTRADICTION` | 직선거리 > 신고연장 (물리적 모순) | 1,709 |
| `SEGMENT_DEGENERATE` | 시작 = 끝 | 394 |
| `SPECIES_MULTI` | 복수 수종 한 칸 기재 | 3,102 |
| `SPECIES_UNMATCHED` | 정규화 후에도 알레르기 DB 미매칭 | 정규화 사전 확정 후 산출 |
| `COUNT_ZERO` | 그루수 0 | 1,249 |
| `STALE` | 기준일자 2022 이전 | 192 |

서울 소스 플래그:

| 코드 | 의미 | 현재 건수 |
|---|---|---:|
| `NOT_A_TREE` | 결주·고사 등 | 303 |
| `SPECIES_INVALID` | 수종 빈값·숫자·기호 | 948 |
| `ROAD_INVALID` | 도로명 무효값 | 7,130 |
| `COORD_LOW_PRECISION` | 좌표 소수 4자리 이하 | 2,525 |
| `COORD_STACKED` | 동일 좌표 10그루 이상 | 3,310 |

**의도적으로 넣지 않는 것**: "좌표거리와 신고연장이 2배 이상 차이" 같은 양방향
기준. 직선거리가 도로연장보다 짧은 것은 정상이며(중앙값 0.83), 양방향으로 재면
3,831건을 잡지만 대부분 오탐이다. 물리적으로 불가능한 방향만 센다.

기관 단위 집계도 산출한다. 오류율 50% 이상인 기관은 개별 레코드가 아니라
기관 단위로 묶어 표시한다.

#### 4.3.4 `public/data/corrections.json` (신규)

```json
{
  "generatedAt": "...",
  "corrections": [
    {
      "sourceType": "streetTree",
      "match": { "institutionNm": "충청북도 옥천군", "sttreeStretNm": "가화길" },
      "field": "startLatitude",
      "from": "26.305441",
      "to": "36.305441",
      "method": "single-digit-repair",
      "confidence": "high",
      "evidence": "정상 끝점에서 0.22km. 한 자리 치환 후보 중 국내에 들어오는 것이 유일"
    }
  ]
}
```

교정은 `method`가 `single-digit-repair`이고 후보가 유일한 경우에만 넣는다.
기관 단위 오류처럼 근거가 약한 것은 교정하지 않고 플래그만 남긴다.

### 4.4 Layer 1 — 로드뷰 메타데이터 검증

`StreetViewModal`은 이미 파노라마 좌표와의 거리를 계산해 3단계 배지를 보여준다.
여기에 `getLocation()`의 나머지 필드를 활용한다.

```javascript
const loc = panorama.getLocation();
// { panoId, title, address, coord, photodate }
```

추가할 검증 축:

1. **촬영 시점 대조** — `photodate`와 데이터 `referenceDate`를 병기.
   "로드뷰 촬영 2024-05 · 데이터 기준 2025-06" 형태. 어느 쪽이 최신인지
   사용자가 판단할 수 있게 한다. 데이터가 로드뷰보다 최신이면 "로드뷰에 안 보여도
   최근 식재되었을 수 있음"이라는 해석이 가능해진다.

2. **도로명 대조** — `address`(파노라마 지점 주소)와 데이터 `roadName`을 비교.
   일치 / 불일치 / 판정 불가 3상태. 서울 소스에서 도로명 칸이 무효값인 7,130그루는
   애초에 비교 대상이 아니므로 "판정 불가"로 둔다.

3. **거리** — 기존 로직 유지. 임계값(50m / 200m)은 그대로 둔다.

**대량 배치 수집은 하지 않는다.** 사용자가 실제로 연 지점만, 그 화면에서만
검증한다. 약관의 "리턴 받는 즉시 1회 자신의 서비스에서 사용" 취지에 맞추고,
무료 이용량도 초과하지 않는다.

검증 결과를 서버나 저장소에 축적하지 않는다. 같은 지점을 다시 열면 파노라마를
다시 조회한다. 세션 내 재조회를 줄이기 위한 메모리 캐시(모달이 닫히면 소멸)는
두되, localStorage 등 영속 저장은 하지 않는다 — 그것이 곧 약관이 금지하는
"결과 데이터의 DB화"에 해당하기 때문이다.

이 판단은 2021년판 약관 PDF를 근거로 한다. 구현 전에 NCP 고객지원으로
현행 약관 기준을 한 번 확인하는 것이 안전하다.

### 4.5 UI

1. **`NOT_A_TREE`는 지도에서 제외한다.** 결주·고사는 나무가 아니다.
   통계에서도 뺀다. FilterPanel에 "원본에 결주·고사로 기재된 303건 제외됨" 표기.

2. **`ROAD_INVALID`는 도로명을 표시하지 않는다.** `"3"`, `"6"`, `"은행나무"`를
   도로명으로 보여주는 건 잘못된 정보다. "도로명 미상"으로 대체.

3. **플래그가 있는 레코드는 마커·폴리라인을 시각적으로 구분한다.**
   기존 healthcare-clean 토큰의 warning 색(`#b45309`)과 점선 스트로크를 쓴다.
   새 색을 도입하지 않는다.

4. **등급 0의 라벨을 "해당없음" → "정보 없음"으로 고친다.** 4.3.2 참조.
   새 상태 키를 추가하지 않으므로 Legend·FilterPanel·StatsPanel은 수정 불필요.

7. **추정 매칭(`matchType: 'inferred'`)은 팝업에 표시한다.** `대왕참나무`가
   `참나무` 기준으로 판정된 것이라면 사용자가 알아야 한다.
   "참나무 기준 추정" 정도의 짧은 주석을 등급 옆에 단다.

5. **FilterPanel에 "품질 이슈 있는 데이터 숨기기" 토글.** 기본값은 표시(off).
   숨기는 게 기본이면 사용자가 데이터가 왜 적은지 모른다.

6. **StreetViewModal의 disclaimer 확장.** 기존 도로명 disclaimer에 더해,
   해당 레코드의 플래그를 근거와 함께 노출한다.

### 4.6 테스트

현재 테스트 프레임워크가 없다. **vitest를 추가한다.**

Layer 0은 전부 순수 함수이므로 테스트하기 쉽고, 반드시 테스트해야 한다.
정규화 사전이 잘못되면 알레르기 등급이 조용히 틀리기 때문이다.

- `speciesCanonical.test.js` — 실측한 라벨을 케이스로. 특히 축약형·오타·복수 수종·비수종 값
- `allergenDatabase.test.js` — 회귀 방지가 목적. `양버즘` → 플라타너스 등급 3이
  나오는지 같은 케이스를 고정한다
- `audit-data.test.js` — 각 플래그가 알려진 입력에서 켜지고 정상 입력에서 꺼지는지
- 좌표 교정 로직 — 검증된 5건이 같은 결과를 내는지, 모호한 입력에서 교정을
  포기하는지

UI는 기존 방식대로 headless Playwright로 배포 후 확인한다.

## 5. 성공 기준

측정 가능한 것으로만 잡는다.

4.3.1의 정규화 사전을 실제 데이터에 적용해 달성치를 미리 계산했다.
아래 목표는 그 계산에 근거한다.

| 지표 | 현재 | 목표 | 근거 |
|---|---:|---:|---|
| 서울에서 알레르기 등급 0으로 표시되는 그루수 | 2,904 | **1,795** | 정규화만으로 716그루 복구, 결주·고사 303 제외, 빈값 948은 `unknown`으로 재분류 |
| 위 1,795를 DB 확장으로 추가 감축 | 1,795 | **5 이하** | 상위 20종(감나무 921, 층층나무 298, 살구나무 217, 산딸나무 106, 모과나무 86 …)이 1,790그루를 덮음. 각 종의 알레르기 등급 근거를 확보한 것만 추가 |
| 알레르기 등급 3 이상인데 0으로 표시 | 28 (`양버즘`) | **0** | 축약형 확장으로 전부 해소 |
| 국토 밖 좌표 | 9 | **0** | 5건 교정, 4건은 교정 불가 → 플래그 후 지도에서 제외 |
| 결주·고사가 나무로 표시 | 303 | **0** | `NOT_A_TREE` 분류 후 제외 |
| 무효 도로명이 화면에 노출 | 7,130 | **0** | "도로명 미상"으로 대체 |
| 복수 수종 중 두 번째 이후 종 정보 소실 | 3,102구간 | **0** | 분해 후 전 종 병기 |

DB 확장 목표를 "0"이 아니라 "5 이하"로 둔 이유는, 알레르기 등급 근거를 찾지 못한
수종은 억지로 등급을 부여하지 않고 `unknown`으로 남기기 때문이다.

## 6. 명시적 비목표

- 공공데이터 원본 수정 — 자치단체·공공데이터포털 권한이며 우리 권한이 아니다
- 로드뷰 이미지 수집·저장 — 약관 위반 소지
- 수종 자동 판별 — 근거상 정확도 미달
- 사용자 신고·크라우드소싱 — 백엔드와 모더레이션이 필요하고 트래픽 전제가 필요
- 기관 단위 좌표 오류의 자동 교정 — 오프셋이 불규칙해 근거가 부족

## 7. 선결 조건

`.env.example`에 `NAVER_GEOCODE_ID` / `NAVER_GEOCODE_KEY`가 문서화되어 있으나
실제 `.env`에는 없다. 4.4의 도로명 대조를 파노라마 `address` 대신 역지오코딩으로
보강하려면 NCP 콘솔에서 발급이 필요하다. **다만 현재 설계는 파노라마 `address`만
쓰므로 필수는 아니다.**
